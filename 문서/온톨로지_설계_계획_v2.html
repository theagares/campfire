온톨로지 설계 계획 v2 — 고정 온톨로지, 회사별 KG

Campfire 게이트웨이 · 2026-09-07 · v1 과 벤치마크 추천을 대체한다. v1 의 선행연구(§2)·한국어 경계(§5)는 그대로 유효.

v3 로 갱신됨

이 문서의 TBox(§2)와 벤치마크 3층(§4)은 유지된다. v3가 바꾼 것: 기밀 판정을 노드 규칙에서 엣지 단위 4층 판정기로, LLM 을 서버(A100)·앱(<10B) 2계층으로, 입력을 문서·회의 전사·메신저로, 모델을 5개사 로컬로. §3 규칙·§5 파이프라인·§6 단계는 v3 가 대체한다.

전제가 바뀌었다. 온톨로지는 고정이고, 어떤 회사 데이터가 와도 그 스키마에 맞는 KG 를 만들어야 한다. 그러면 v1 의 결론 하나가 뒤집힌다 — “기밀 탐지 벤치마크는 공개 데이터가 없다”가 “회사 데이터와 정답 KG 가 함께 있는 소스가 실제로 있다”로.

0무엇이 바뀌었나

v1 — 회사가 온톨로지를 채운다

클래스 8종은 기밀 범주(코드명·고객사·재무지표…).
회사마다 인스턴스를 등록 → 사전 매칭.
“잘 만들었는가”를 잴 방법이 없다 — 정답이 회사마다 다르니까.

v2 — 온톨로지는 고정, 회사 데이터로 KG 를 채운다

클래스는 회사가 가진 것(조직·사람·직무·프로젝트·제품·계약·재무사실·자산).
기밀은 클래스가 아니라 KG 위의 규칙.
“이 스키마에 맞는 KG 를 정확히 뽑았는가”는 잴 수 있는 질문이다.

가장 큰 구조 변화 — 기밀 클래스가 사라진다

v1 의 CLIENT 를 보자. 삼성전자는 어떤 회사에겐 고객사고 다른 회사에겐 경쟁사다. 고정 온톨로지에서 이건 클래스가 될 수 없다 — 회사에 따라 답이 달라지는 것은 클래스가 아니라 관계다. Organization 하나에 customerOf / competitorOf 관계가 붙는다. PROJECT_CODENAME 도 마찬가지로 Project 노드 + 공개 여부 속성이 된다. v1 클래스 8종은 전부 이렇게 노드 + 관계 + 규칙으로 풀린다(§2 끝의 표).

1왜 이게 더 낫나 — 확립된 문제가 된다

“고정 온톨로지에 맞춰 텍스트에서 KG 를 뽑는다”는 ontology-guided KG construction 이라는 이름이 있는 문제고, 전용 벤치마크가 있다.

Text2KGBench (ISWC 2023)내용
과제주어진 온톨로지(클래스·정규 관계명·domain/range)에 엄격히 맞는 트리플 추출
지표 7개① 사실 추출 P/R/F1  ② 온톨로지 적합률(생성 트리플 중 정규 관계 비율)  ③ 환각 3종 — 주어·관계·목적어
데이터Wikidata-TekGen 10개 온톨로지 13,474문장 / DBpedia-WebNLG 19개 온톨로지 4,860문장

데이터는 위키라 우리 입력과 다르지만, 지표 7개와 “온톨로지 적합”이라는 평가 축이 그대로 우리 것이다. 특히 관계 환각 지표는 v1 §2-⑤ 에서 확인한 “LLM 은 관계를 지어낸다”를 정량화하는 바로 그 숫자다.

그리고 결정적으로, 회사 데이터에 정답 KG 가 붙어 있는 소스가 있다. §4.

2TBox — 고정 온톨로지

원칙 하나: 표준 어휘를 재사용한다. 조직·사람·직무는 W3C 가 이미 권고안으로 정해놨고, 계약 조항은 CUAD 가 41종으로 분류해놨다. 새로 짓는 건 회사 문서에 특유한 것뿐이다.

관계 — domain/range 를 반드시 붙인다

subOrganizationOf   Organization → Organization
memberOf            Person → Organization   (via Membership, with Role)
customerOf          Organization → Organization
suppliesTo          Organization → Organization
competitorOf        Organization → Organization

domain/range 가 있어야 Text2KGBench 의 적합률·환각 지표가 계산된다. 그리고 LLM 이 만든 트리플을 제약으로 거른다 — hasClause(Person, …) 같은 건 프롬프트를 고치는 게 아니라 스키마가 거부한다. v1 §2-⑤ 의 “LLM 에게 관계를 맡기지 않는다”가 v2 에선 “맡기되 스키마로 검증한다”로 바뀐다. 더 강한 장치다.

3기밀은 클래스가 아니라 규칙이다

온톨로지가 고정이면 기밀도 회사 무관하게 성립하는 구조적 규칙이어야 한다. “이 회사의 기밀 목록”을 받는 게 아니라, KG 의 모양에서 위험을 읽는다.

공개성(publicness) — 기밀을 “목록으로 받지” 않고 “공개에서 뺀다”

공시(DART·EDGAR)에 있는 사실은 정의상 공개다. 그러면 회사 문서에서 뽑은 KG 중 공시 KG 에 없는 부분이 기밀 후보다. 회사마다 다른 기밀을 고정 규칙으로 다루는 방법이 이것이다 — 기밀 목록은 회사마다 다르지만 “공개된 것을 뺀 나머지”라는 연산은 회사와 무관하다.

이게 v1 의 “빈 온톨로지 문제”(§7)를 없앤다. 채울 목록이 없다. 공시가 음성 공간을 그려준다.

정직한 한계

비상장사는 공시가 없다. 그 경우 publicness 는 회사 홈페이지·보도자료로 대체하거나 사용자가 “공개” 표시를 해야 한다. 이건 규칙이 틀린 게 아니라 음성 공간의 출처가 달라지는 것이다. 1차 목표는 상장사 — 정답이 있는 곳부터.

OpenDART 가 이 계획의 축이다

같은 회사의 공시가 구조화 API 와 서술형 사업보고서로 동시에 존재한다. API 응답이 정답 KG, 사업보고서가 입력. 라벨링 0으로 한국어 회사 KG 벤치마크가 생기고, 회사를 바꿔가며 돌리면 “어떤 회사가 와도”가 N개 회사에 대한 실측이 된다.

임원 현황(2019010) → Person —memberOf→ Org (with Role, 취임일) 타법인 출자현황(2019015) → Org —investsIn→ Org (목적, 금액) 최대주주 현황(2019007) → Person|Org —shareholderOf→ Org (지분율) 감사용역 체결(2020010) → Org —auditedBy→ Org 직원 현황(2019011) → Org —hasFact→ FinancialFact(headcount) 배당·증자(2019005/4) → Org —hasFact→ FinancialFact

Tier 2 · 온톨로지 적합 · 환각

Text2KGBench 지표 7개를 Tier 1 출력에 그대로 적용한다. “고정 온톨로지” 주장의 검증이 여기서 이뤄진다 — 적합률이 낮으면 TBox 가 회사 문서에 안 맞는 것이고, 관계 환각이 높으면 LLM 을 스키마가 못 잡고 있는 것이다. 둘은 다른 실패라 다른 지표가 필요하고, 그래서 7개다.

Tier 3 · 기밀 규칙

규칙정답 출처

헤드라인 지표는 평균이 아니라 최소값과 분산이다

“어떤 회사가 와도”는 업종이 다른 N개 회사에서 KG F1 의 분산이 낮다는 뜻이고, 그건 잴 수 있다. 평균 F1 80 에 최소 40 이면 어떤 회사에선 안 되는 것이다. 제조·IT·금융 최소 3업종, 회사 10개로 시작한다.

5파이프라인

문서 ──파싱(있음)──▶ 텍스트 ──KG 추출──▶ (엔티티, 타입) + 트리플 로컬 LLM + 온톨로지 프롬프트 ──스키마 검증──▶ domain/range 위반 폐기 환각 차단 ──저장──▶ SQLite 노드·엣지 기존 store, 그래프DB 안 씀 ──공개성──▶ 공시 KG 와 대조 → public 표시 사용자 프롬프트/첨부 ──연결──▶ 스팬 → KG 노드 v1 AC 매처 그대로 ──규칙 R1~R6──▶ 위험도 ──마스킹(있음)──▶ 외부로
  • KG 추출은 오프라인 배치 — v1 §8 의 논리 그대로. 실시간 경로는 연결+규칙뿐이라 빠르다
  • 탐지가 v1 보다 단순해진다 — 사전 매칭 + 조합 규칙이 “KG 노드 연결 + 이웃 조회”가 된다
  • 로컬 전용 제약 유지 — 회사 문서 전체가 KG 추출기를 지나는데, 이게 외부로 나가면 게이트웨이가 유출 경로가 된다

7v1 에서 살아남는 것 · 죽는 것

죽는다

  • 기밀 클래스 8종 → 노드·관계·규칙
  • company.yaml 인스턴스 목록 → KG
  • “빈 온톨로지 문제” → 채울 목록이 없다
  • 추천서 §0 “기밀 탐지에 공개 데이터 없다” → 프레임이 바뀌어 있다
  • 후보 추출 4신호(C-value 등) → KG 추출로 흡수. C-value 는 Project 이름 후보에만 남는다

살아남는다

  • 선행연구 §2 전부 — 특히 quasi-identifier(R6), LLM 관계 환각(스키마 검증), 추출≠탐지
  • 한국어 경계 §5 — 연결기가 그대로 쓴다
  • AC 매처, 로컬 전용, 승인 UI, 그래프 뷰
  • KDPII·KLUE-NER — 각각 PII 재현율, 경계 채점. 목적 그대로
  • 주입 벤치마크 — R6 전용으로 축소

8정직하게 남는 것

  • OpenDART 정답은 공시된 사실뿐이다. Tier 1 은 “KG 를 잘 만드나”이지 “기밀을 잘 잡나”가 아니다. 기밀 자체의 정답은 여전히 CUAD(영어)와 합성 주입뿐 — 한국어 기밀 정답은 아직도 합성이다.
  • 고정 온톨로지의 고유한 위험 — 너무 일반적이면 쓸모없고, 너무 구체적이면 어떤 업종엔 안 맞는다. §4 의 분산 지표가 이걸 잡아야 하고, 못 잡으면 TBox 를 고쳐야 한다. 0단계는 “확정”이 아니라 “초안”이다.
  • REFinD 는 비상업 — 평가에만 쓴다. FinRED 라이선스는 미확인.
  • Text2KGBench 데이터 자체는 안 쓴다 — 위키 문장이라 회사 문서와 다르다. 지표만 가져온다.

9첫 액션

  1. OpenDART 인증키 발급 — 회원가입이 필요해서 사람이 해야 한다
  2. 회사 10개 선정(제조·IT·금융 3업종+) → API 6종 호출 → 트리플 수 세기. 코드 한 줄 전에 “정답 KG 가 회사당 몇 개 트리플인가”를 안다. 너무 적으면 API 를 더 붙인다
  3. 같은 회사 사업보고서 PDF 를 우리 파서에 통과 → 텍스트가 제대로 나오는지. 여기서 막히면 2단계가 무의미하다
  4. 그다음 TBox 를 실제 트리플에 대보고 고친다 — 0단계는 2번 결과를 보고 끝난다
