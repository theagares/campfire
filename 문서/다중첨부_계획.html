다중 첨부 — 배치 접수, 순차 검사, 탭 검토

2026-09-18 · 파일을 한 배치로 보존하고, 실제 프롬프트 문맥으로 하나씩 검사한 뒤 정확히 한 번 주입한다

문제는 한 변수가 아니라 단일 파일 계약 전체다

content.js:722 의 pendingAttachment 가 단수인 것이 최초 손실 지점이지만, 수집·검사·패널 결정·주입·MAIN world 승인도 모두 파일 하나를 전제로 한다. 따라서 배열로 바꾸는 패치가 아니라 첨부 이벤트 하나를 보존하는 배치 계약으로 바꿔야 한다.

2먼저 고정할 정책과 자료구조

MVP 정책 — 구현 전에 확정

  • 한 배치 최대 5개, 배치 원본 총량 최대 20MB. 초과하면 일부만 받지 않고 배치 전체를 거절한다. 파일당 20MB는 우리가 새로 정하는 값이 아니라 엔진이 이미 강제하는 MAX_UPLOAD_BYTES(config.py:64, 초과 시 jobs.py:94에서 거부)와 같은 값이다. 클라이언트 검사는 왕복을 아끼는 선검사이지 상한의 출처가 아니다.
  • 크기와 개수는 fileToBase64() 전에 검사한다. 한 번에 모든 파일을 base64로 보관하지 않는다.
  • 지원 파일이 하나도 없는 배치는 가로채지 않고 원래 사이트 동작에 맡긴다. 지원+미지원 혼합 배치만 전체 이벤트를 보류한다. 그래야 보호 대상이 없는 첨부까지 불필요하게 패널과 재주입 경로를 타지 않는다.
  • 파싱 실패·검사 오류·타임아웃은 기본 fail-closed. 사용자가 해당 파일을 명시적으로 제거하거나 재시도해야 전송할 수 있다.
  • 텍스트 잘림(truncated)도 fail-closed 에 포함한다. 엔진은 추출 텍스트가 MAX_TEXT_CHARS(20만 자, config.py:75)를 넘으면 앞부분만 검사하고 result["truncated"]로 알린다(orchestrator.py:355). 그런데 확장에서 이 값을 읽는 코드가 지금 한 줄도 없다 — 뒷부분을 아예 안 본 파일이 패널에 “검사 완료”로 뜬다. 배치를 5개 × 20MB 로 키우는 변경이라 만날 확률이 올라가므로, truncated인 파일은 탭에 “부분만 검사됨”으로 고지하고 자동 전송하지 않는다. 엔진 결과에 기존 stats.originalLength의 뜻을 바꾸지 말고 stats.scannedLength와 자르기 전 stats.sourceLength를 함께 넣어 실제 범위를 보여준다. 선택지는 “검사된 앞부분만 새 파일로 전송”, “검사하지 않은 원본 전체 전송(위험 확인 2회)”, “파일 제외” 세 개다. 첫 선택은 뒷부분이 제거되는 결과임을 파일명(_partial_masked.md)과 경고에 명시한다. 같은 상한으로 하는 재시도는 결과가 달라지지 않으므로 제공하지 않는다.
  • 지원/미지원 혼합 배치에서는 미지원 파일을 탭에 남기고 기본 제외한다. 사용자가 “검사 없이 원본 포함”을 직접 선택한 경우에만 통과시킨다.
  • 전송 버튼은 모든 항목이 검사 완료 또는 사용자 결정 상태가 된 뒤에만 활성화한다.
  • 검토 중 들어온 새 배치는 거절한다. 패널이 열려 있어도 페이지는 계속 살아 있어 사용자가 파일을 또 붙일 수 있다. 그때 pendingBatch를 덮어쓰면 배치 A의 injectionContext가 사라져 “마지막 것만 된다”는 원래 버그가 배치 단위로 그대로 재현된다. 새 배치는 원래 이벤트째로 막고 “검토 중입니다”만 알린다. 큐에 쌓지 않는 이유는, 큐는 배치별 주입 컨텍스트를 언제까지 유효하게 들고 있을지를 정해야 하고 그 답이 사이트마다 다르기 때문이다. MVP에서는 거절이 유일하게 확실한 동작이다.

action은 상태별 허용표로 검증한다

partial은 “일부 마스킹 해제”와 “잘린 앞부분 전송”을 동시에 뜻할 수 있어 scanned-prefix로 이름을 고정한다. 정상 검사 파일은 masked(일부 unmaskedKeys 허용)·original·exclude, truncated 파일은 scanned-prefix·위험 확인을 마친 original·exclude, 미지원 파일은 명시적으로 고른 original·exclude, 오류 파일은 재시도 전까지 exclude만 허용한다. 인젝션 정책이 block인 항목은 exclude 외 결정을 받지 않는다. SW는 ID 존재 여부, 상태별 action, 키 prefix·범위·중복을 모두 검사하고 하나라도 어긋나면 배치 전체 결정을 거절한다. truncated 원본 전체를 보낼 때의 두 번째 확인은 패널이 정확한 riskAck:'send-unscanned-original'을 붙이고 SW가 그 action에서만 요구한다. 다른 action에 riskAck가 붙어도 거절한다. original/exclude에는 unmaskedKeys와 artifactId가 없어야 하고, 탐지 항목을 전부 해제한 masked 결정은 original로 정규화한다. SW→content의 promptText는 빈 문자열도 유효한 명시값이므로 타입으로 검사하고, 누락·잘못된 타입이면 캡처한 원문으로 폴백하지 않고 전체를 중단한다.

수집은 첫 await 전에 끝낸다

input/drop/paste 캡처 리스너는 이벤트 진입 즉시 전체 FileList를 배열로 복사하고 지원 여부·개수·원본 총량을 계산한다. 지원 파일이 하나라도 있으면 같은 동기 구간에서 preventDefault· stopImmediatePropagation, input 비우기, pendingBatch 할당까지 끝낸 뒤에만 패널 열기나 메시지 같은 비동기 작업을 시작한다. 한 파일씩 base64로 바꾸는 일은 lease 뒤다. 한도를 넘었거나 이미 배치가 있으면 원래 이벤트를 막고 input을 비운 채 오류만 보여주며, 기존 pendingBatch는 건드리지 않는다. 지원 파일이 0개면 어떤 이벤트도 막지 않는다. 이렇게 해야 첫 await 사이에 사이트 리스너나 두 번째 첨부가 원본 목록을 보거나 상태를 덮지 않는다.

숫자 offset 대신 안정적인 항목 키를 쓴다

검사가 진행되는 동안 탭이 추가되고 실패 항목이 생기므로 누적 offset을 다시 계산하면 사용자가 이미 바꾼 마스킹 선택이 다른 항목을 가리킬 수 있다. buildSegments()에 keyPrefix를 주고 계약서-id:0, prompt:0처럼 만든다. data-idx도 숫자 변환하지 않고 문자열로 처리한다. 이 키는 세션 복구와 파일별 결정에도 그대로 사용한다.

순차 처리는 지연 최소화가 아니라 메모리 상한을 택한 결정이다. 엔진의 GPU 구간은 detector별 _request_lock으로 직렬화되지만, orchestrator.py:144~156 주석대로 Solar 네트워크 대기는 락 밖에서 청크끼리 겹치므로 파일까지 병렬화하면 전체 시간이 줄 가능성은 있다. 다만 파일 N개 × 청크의 DETECT_CONCURRENCY 팬아웃과 여러 base64 복사본이 함께 살아 메모리 상한이 깨진다. MVP는 예측 가능한 메모리, 정확한 진행률, 파일별 오류 격리를 우선해 한 파일의 응답 뒤 다음 파일을 인코딩한다. 성능 수치가 필요하면 구현 뒤 동일 배치로 순차/제한 병렬을 따로 벤치마크하며, 현재 문서에서 “병렬화해도 시간 이득이 없다”고 단정하지 않는다.

파싱 타임아웃 뒤의 스레드는 실제로 끝난 것이 아니다

orchestrator.py:36~53의 asyncio.to_thread(parse_document)는 wait_for가 타임아웃돼도 작업 스레드를 죽이지 못한다. 따라서 timeout 파일 뒤에 다음 파일을 바로 시작하면 확장 쪽은 순차여도 엔진 파서는 겹친다. 엔진에 단일 active_parse_task 슬롯을 두고 타임아웃된 task를 완료 시점까지 추적한다. 그동안 새 파싱 요청은 새 스레드를 만들지 않고 parser_busy로 즉시 fail-closed한다. 배치에서 timeout/parser_busy가 나오면 남은 파일을 시작하지 않고 “엔진 파서 정리 후 재시도” 상태로 끝낸다. 근본적인 강제 종료는 별도 프로세스 파서가 필요하지만, 이 가드만으로 타임아웃마다 고아 파싱 스레드가 누적되는 것은 막을 수 있다.

전역 큐는 인코딩보다 먼저 lease를 준다

SW 안에서 HTTP 요청만 직렬화하면 늦다. 두 탭의 content가 각각 fileToBase64()를 끝낸 뒤 메시지를 보내면 큐에서 기다리는 동안 큰 문자열 두 개가 동시에 살아 있다. START_MULTI_SCAN은 즉시 queued 상태만 응답하고, 실제 차례가 왔을 때 SCAN_LEASE_GRANTED {sessionId, leaseId}를 보낸다. grant 상태를 먼저 storage에 확정하며 이 메시지는 힌트일 뿐이다. content는 유실에 대비해 GET_MULTI_SCAN_STATUS {sessionId,clientBatchNonce}를 backoff polling하고, persisted status:'granted'와 같은 leaseId를 받은 뒤에만 인코딩한다. content는 grant를 확인하기 전에는 File 객체만 보존하고 인코딩하지 않는다. lease는 prompt부터 마지막 item까지 한 배치의 검사 구간만 감싼다. 정상은 finish, 치명 오류·사용자 취소·소유 문서 종료는 ABORT_MULTI_SCAN 상태 전이로 끝낸다. 단, 엔진 HTTP가 이미 진행 중이면 UI와 세션은 즉시 취소하되 lease는 draining으로 두고 그 요청이 실제 settle될 때까지 다음 배치에 주지 않는다. fetch만 끊고 곧바로 다음 요청을 보내면 서버의 기존 추론은 계속 돌아 두 작업이 겹칠 수 있기 때문이다. 요청이 없을 때는 즉시 해제한다. SW 재시작 시 대기 세션은 저장된 seq 순서로 다시 큐에 넣고, 실행 중이던 세션은 오류로 바꿔 재시도를 요구한다. 복구 직후에는 이전 SW가 시작한 서버 작업이 남았을 수 있으므로 GET /activity가 busy:false를 확인하기 전 새 lease를 grant하지 않는다. activity 조회 실패나 비정상 장기 busy는 원본을 인코딩하지 않은 채 엔진 사용 중/복구 오류로 fail-closed한다.

grant 이후의 SCAN_MULTI_PROMPT, 모든 SCAN_MULTI_ITEM, FINISH_MULTI_SCAN/ABORT_MULTI_SCAN에는 반드시 {sessionId, leaseId, requestId, itemSeq, itemId}를 넣는다. prompt는 {itemSeq:0,itemId:'prompt'}, 문서는 스테이징 순서대로 1..N과 docId, finish는 {itemSeq:N+1,itemId:null}이다. SW는 현재 lease 소유 tabId+frameId+documentId와 세션, 예상 순번·itemId를 모두 대조한다. 이미 완료된 것과 같은 requestId 재전송은 저장된 ACK를 돌려주고 엔진을 다시 호출하지 않는다. 아직 처리 중인 같은 requestId는 기존 in-flight Promise의 결과에 합류시키고 두 번째 엔진 요청을 만들지 않는다. 같은 순번의 다른 requestId·역전 메시지·취소된 lease·다른 문서의 lease·전체 문서 처리 전 finish는 상태를 바꾸지 않고 거절한다. finish도 같은 requestId에 한해 멱등이며 lease 해제 뒤 도착한 늦은 엔진 응답은 폐기한다. parser timeout/busy의 abort는 아직 보내지 않은 나머지 문서를 skipped-after-parser-timeout 오류로 확정하고 ready 상태로 넘어가며, 사용자는 성공 파일만 보내거나 오류 파일을 제외할 수 있다. 사용자 취소 abort는 세션 전체를 즉시 닫는다.

프롬프트는 맨 처음 검사하되, 파일 요청마다 엔진이 다시 로컬 검사한다

현재 scanCombined()는 문서 인젝션이 사용자의 실제 지시와 충돌하는지 판단하기 위해 POST /jobs에 userPrompt를 보낸다. 다중 검사도 각 파일마다 반드시 같은 값을 보낸다. 같은 프롬프트를 N번 다시 검사하는 낭비를 줄이려고 scanUserPrompt=false 같은 건너뛰기 플래그를 넣고 싶어지는데, 그 순간 원문이 외부로 나간다. 체인이 이미 그렇게 연결돼 있다:

  • orchestrator.py:277 — 프롬프트를 검사해야 user_prompt_masked가 만들어진다. 건너뛰면 None.
  • orchestrator.py:167 — None이면 meta["user_prompt_masked"] 키 자체를 넣지 않는다.
  • llm_mcp.py:564 — meta_d.get("user_prompt_masked", user_prompt). 키가 없으니 원문으로 폴백해 Upstage Solar로 나간다. 파일마다 한 번씩, 총 N번.

/jobs/prompt는 패널에 프롬프트 탐지 결과를 먼저 보여주기 위한 호출일 뿐, 이후 요청의 보안 증명으로 사용하지 않는다. 각 POST /jobs에는 userPrompt 원문만 보내고 엔진이 기존 단일 경로와 동일하게 PII를 다시 로컬 검사해 user_prompt_masked를 만든다. 클라이언트가 보낸 userPromptMasked는 받지 않거나 무시한다. 호출자가 원문을 “마스킹됨”이라고 속여 외부 모델로 내보낼 수 있는 신뢰 경계를 만들지 않는 것이 우선이다. 비용은 짧은 프롬프트의 로컬 검사 N회이며, 문서 파싱·청크 검사와 Solar 호출에 비해 작다. 나중에 최적화가 필요하면 서버가 발급하고 원문 해시와 결합한 불투명 promptContextId만 별도 설계한다.

프롬프트 원문은 SCAN_MULTI_PROMPT에서 SW 세션에 정확히 한 번 저장하고, 이후 content가 파일마다 다시 보내지 않는다. SW가 모든 /jobs에 그 동일 문자열을 넣는다. 패널 표시와 최종 promptText의 유일한 기준은 첫 /jobs/prompt 결과다. 각 파일 응답의 userPromptOriginal· userPromptMasked·userPromptPiiItems는 그 파일의 Solar 호출을 안전하게 만들었다는 결과일 뿐 UI나 최종 결정의 입력으로 합치지 않고 저장 전에 제거한다. 파일 수만큼 프롬프트 원문과 탐지 배열을 중복 저장하거나, 마지막 파일 결과가 첫 결과를 덮는 일을 막는다.

프롬프트 검사가 실패하면 배치 전체를 fail-closed 처리한다. 또한 파일별 /jobs에서 프롬프트 재검사나 마스킹 생성이 실패해도 해당 파일을 오류로 두고 전송하지 않는다.

세션 소유자는 탭이 아니라 문서다

manifest가 두 content script를 모두 all_frames:true로 실행하므로 tabId만 확인하면 같은 탭의 다른 iframe이 세션 메시지를 보낼 수 있다. START 시 sender.tab.id, sender.frameId, sender.documentId를 SW가 직접 기록하고 content가 보낸 소유자 필드는 신뢰하지 않는다. 이후 lease·item· artifact META/CHUNK/ACK·decision pull·finalize는 이 세 값이 모두 같은 sender만 허용한다. lease가 끝난 뒤의 요청은 세션의 clientBatchNonce도 일치해야 한다. SW→content 결정도 chrome.tabs.sendMessage의 frameId/documentId 옵션으로 정확한 문서에만 보낸다. 최상위 문서의 tabs.onUpdated(status:'loading')와 탭 닫힘은 즉시 정리하고, 자식 frame만 사라져 종료 신호를 못 받은 경우는 짧은 세션 watchdog이 정리한다. 늦게 도착한 이전 documentId 메시지는 항상 거절한다.

문서 내용은 디스크에 쓰지 않는다 — 그래서 IndexedDB가 아니다

무거운 결과를 어디에 둘지는 성능 문제처럼 보이지만, 이 코드베이스에서는 이미 내려진 보안 결정이다. service-worker.js:282 주석이 그대로 적어두고 있다 — “chrome.storage.session 은 브라우저 세션 동안만 살아 있고 디스크에 남지 않는다 — 검토 중인 문서 내용이 들어가므로 local 이 아니라 session 이어야 한다.” IndexedDB는 디스크 저장소이고, 옮기려던 originalText·전체 segments·마스킹 바이너리가 바로 그 “검토 중인 문서 내용”이다. TTL 스윕은 얼마나 오래 남는지를 줄일 뿐 디스크에 쓰이는지를 되돌리지 못한다. 기밀 유출을 막는 게이트웨이가 방금 검사한 기밀을 평문으로 프로필 폴더에 떨어뜨리는 건 방향이 반대다. 그래서 저장 계층은 디스크로 내려가지 않는다:

  • 메타 + originalText + 탐지 항목(piiItems/injectionItems) → chrome.storage.session. 지금과 같다. 메모리 기반이고 브라우저를 닫으면 사라진다. segments 는 저장하지 않는다 — buildSegments()(sidepanel.js:80) 출력은 {type:'text', text}와 {type:'item', original}이라 그 자체가 문서 텍스트 전체다. 둘 다 저장하면 같은 본문을 두 벌 갖게 된다. maskedText, maskedFile, 전체 progress 배열도 세션에서 제외하고 진행률은 파일별 최신 단계와 퍼센트만 저장한다.
  • 검사 중에는 마스킹 바이너리를 만들거나 저장하지 않는다. 다중 경로의 /jobs는 wrapFile=false를 보낸다. 완전 마스킹과 부분 해제 모두 결정 시점에 저장된 텍스트+항목으로 최종 문자열을 만든 뒤 SW의 하나의 표준 wrapper로 .md를 생성한다. 따라서 SW 재시작 여부에 따라 DOCX/MD가 달라지지 않는다. 새로 만드는 것은 없다 — 셋 다 이미 있다: run_pipeline의 wrap_file은 orchestrator.py:192에 있고 기본값이 이미 False다. POST /jobs만 jobs.py:113에서 wrap_file=True를 하드코딩하고 있으므로, 폼 필드를 받아 그 자리에 넘기고 필드가 없으면 True로 두면 단일 경로는 그대로다. MD wrapper도 service-worker.js:18이 wrapMaskedFile을 이미 import 하고 :587의 WRAP_MASKED_TEXT 핸들러가 이미 쓰고 있다(manifest 가 type:module이라 배선도 끝나 있다). 따라서 이 단계의 실제 작업은 기존 파라미터를 폼으로 노출하고, 기존 wrapper를 masked와 scanned-prefix 산출물에 호출하는 것이다. original은 content가 가진 원래 File을 쓰고 exclude는 파일을 만들지 않으므로 wrapper 대상이 아니다.
  • 결정 뒤의 전송 대기 artifact만 sessions 바깥 SW 메모리 Map에 잠시 둔다. 세션에는 artifact ID·문서 ID·action·소유 tabId/frameId/documentId·pending|delivered 상태 같은 재생성 가능한 descriptor만 저장한다. SW가 재시작하면 pending artifact만 같은 텍스트·항목· unmaskedKeys로 다시 만들며, 불가능하면 stale로 닫는다. delivered artifact는 재생성하거나 다시 내려주지 않는다.
  • 따라서 IndexedDB도 chrome.alarms도 쓰지 않는다. 다만 setTimeout만으로 둔 watchdog은 SW 재시작 때 사라지므로 세션별 expiresAt은 저장하고, hydration과 모든 세션 메시지 진입 때 만료 세션을 먼저 쓸어낸다. 별도 alarm 권한 없이도 다음 활동 시 확실히 회수되며, 브라우저가 계속 열려 있어도 stale 세션이 영구히 남지 않는다. manifest 권한은 현재의 activeTab·scripting·sidePanel·storage·tabs에서 늘지 않는다(alarms는 지금 선언돼 있지도 않다).

10MB 쿼터는 확장 전체 한도다. 파일 5개 × 20만 자 계산은 배치 하나에만 해당하고, 서로 다른 탭의 검토 세션은 합산된다. persistSessions()를 fire-and-forget으로 두거나 오류를 삼키지 않고 await persistSessionsOrThrow()로 바꾼다. 모든 상태 쓰기는 하나의 stateWriteChain 안에서 snapshot 생성부터 storage.session.set() 완료까지 직렬화하고, 단조 증가 stateRevision으로 오래된 쓰기가 최신 draft를 덮지 못하게 한다. 모든 읽기·변경 핸들러는 같은 체인 안에서 ensureHydrated()를 먼저 완료하며, hydration 실패를 “메모리로만 계속” 처리하지 않고 새 작업을 fail-closed한다. 한 transaction 실패가 Promise chain 전체를 영구 reject시키지 않도록 다음 작업은 stateWriteChain.then(tx, tx) 형태로 연결하고 각 호출자에게 자기 오류를 반환한다.

이전 안의 reservedBytes 선예약은 제거한다. MAX_TEXT_CHARS는 본문만 제한하고 탐지 항목 배열에는 고정 상한이 없어 START 시 “최악 크기”를 정확히 계산할 수 없기 때문이다. 대신 엔진 응답에서 허용 필드와 유효한 offset만 정규화하고, 파일 응답의 중복 userPrompt*·maskedText·maskedFile·전체 progress를 제거한 후보 snapshot을 만든다. 같은 write chain 안에서 UTF-8 직렬화 크기와 storage.session.getBytesInUse(null)/getBytesInUse(SESSION_STATE_KEY)를 확인해 전체 현재 사용량 - 현재 state key 사용량 + 후보 state 크기가 확장 전체 8MB soft limit 안일 때만 원자적으로 교체한다. 탐지 항목이 비정상적으로 많아 후보가 한도를 넘으면 그 큰 결과는 Map에도 확정하지 않고 해당 파일을 result-too-large 오류 메타로 바꾼 작은 snapshot만 저장한다. set/get/hydration이 실패해도 기존 snapshot은 지우지 않고 새 세션 또는 새 결과만 fail-closed한다. 저장 성공을 확인한 뒤에만 패널 메시지를 보낸다.

PANEL_SCAN_INIT/ITEM/DONE을 보낼 때도 세션 상태를 먼저 저장하고 성공을 기다린다. 패널에서 탭을 바꾸거나 마스킹/제외 선택을 수정할 때마다 PANEL_DRAFT_UPDATE로 activeTab, 안정적인 unmaskedKeys, 파일별 decision을 SW에 저장한다. 따라서 패널 재로드 후 PANEL_READY 스냅샷으로 검사 결과뿐 아니라 미완료 선택도 복구된다. 패널 결정은 종료가 아니다. 정상 결정 시 세션을 awaiting-injection으로 바꿔 유지하고, content의 FINALIZE_MULTI_SESSION을 받은 뒤에만 세션과 남은 artifact를 지운다. 취소·타임아웃·탭 종료는 주입할 것이 없으므로 즉시 정리한다. 페이지가 실제로 새 문서로 교체될 때(tabs.onUpdated의 changeInfo.status === 'loading')와 탭이 닫힐 때(tabs.onRemoved) 세션을 stale로 만들고 산출물을 정리한다. SPA의 history/hash URL 변경만으로는 세션을 취소하지 않는다. 서비스 워커가 검사 도중 재시작되면 미완료 항목을 오류로 바꾸고 재시도를 요구한다. kind:'multi'는 명시적으로 분기하며 알 수 없는 kind를 프롬프트 검사로 폴스루시키지 않는다.

세션 수명과 전역 직렬화 계약

startPanelSession()처럼 “한 번 보내고 한 번 기다리는” 함수는 분할 메시지와 맞지 않는다. createPanelSession({kind:'multi', itemsMeta})가 content가 배치 캡처 때 한 번 만든 startRequestId/clientBatchNonce와 함께 START_MULTI_SCAN을 보내고, SW가 sender에서 소유 문서를 확정하고 충돌 없는 sessionId를 발급한 뒤 {sessionId, decisionPromise}를 반환하게 한다. START 응답이 유실돼 같은 소유 문서가 같은 startRequestId를 재전송하면 기존 sessionId를 멱등 반환하고, 다른 startRequestId는 활성 배치 중복으로 거절한다. content가 만든 tabId/sessionId를 권한 근거로 쓰지 않는다. 호출자는 발급받은 sessionId로 prompt/item/finish를 차례로 보낸 뒤 마지막에 await decisionPromise한다. 결정 뒤 artifact 수령과 주입을 마치면 성공/부분 성공/실패 정보를 담아 FINALIZE_MULTI_SESSION을 반드시 보내며, finally에서도 실패 finalize를 시도한다. 같은 탭의 중복 배치는 content와 SW 양쪽에서 거절하고, 서로 다른 탭의 배치도 SW의 전역 검사 큐/뮤텍스를 거쳐 한 번에 하나만 엔진으로 보낸다. 그래야 탭 두 개가 동시에 base64와 엔진 청크를 쌓아 순차 처리의 메모리 상한을 깨지 않는다. 취소·탭 종료는 큐의 대기 작업도 제거한다.

큐는 FINISH_MULTI_SCAN에서 해제한다 — 검토 대기는 큐를 잡지 않는다. 큐를 두는 이유가 검사 구간의 메모리이므로 사람이 패널을 보고 있는 시간까지 잡을 근거가 없고, decisionPromise까지 뮤텍스로 감싸면 탭 B가 탭 A의 사용자가 결정을 누를 때까지 상한 없이 막힌다. 패널은 setOptions({tabId, path})로 이미 탭별이라 두 탭이 동시에 검토 상태여도 충돌하지 않는다. 동시 검토를 막는 규칙은 탭 단위(같은 탭의 새 배치 거절) 하나뿐이다.

  • truncated 탭은 실패가 아니라 부분 검사로 따로 표시하고 검사 200,000자 / 전체 N자를 보여준다. “앞부분만 새 파일”, “미검사 원본 전체(2회 확인)”, “제외” 중 하나를 고르기 전에는 전송할 수 없다
  • 실패 파일은 “재시도” 또는 “이 파일 제거”, 미지원 파일은 “원본 포함” 또는 “제거” 중 하나를 사용자가 골라야 한다
  • 전송 버튼은 전부 끝나고 모든 오류 항목에 결정이 있어야 열린다. 라벨도 2개 전송 · 1개 제외처럼 실제 결과를 밝힌다
  • 탭은 role="tablist"/role="tab", 방향키 이동, 포커스 표시, 좁은 패널에서 가로 스크롤을 지원한다

브로드캐스트에는 메타만, 본문은 현재 탭이 pull 한다

PANEL_SCAN_ITEM/PANEL_SCAN_PROMPT는 전역 runtime 채널을 지나므로 {sessionId, tabId, itemId, status, counts} 메타만 알린다. 파일은 docId, 프롬프트는 고정 itemId:'prompt'를 쓴다. 이 broadcast도 갱신 힌트이며, 패널은 non-terminal 세션 동안 메타 snapshot을 backoff polling해 알림 유실을 복구한다. 패널은 활성 탭을 그릴 때 GET_PANEL_ITEM_RESULT {sessionId, itemId}를 보내고, SW는 메시지의 tabId를 신뢰하지 않고 sender.url이 정확히 chrome-extension://…/sidepanel/sidepanel.html?tabId=N인지 파싱해 얻은 N과 세션 소유 tabId를 확인한 뒤 그 항목의 originalText, piiItems, injectionItems만 반환한다. 패널 재로드의 PANEL_READY도 문서 본문 전체를 한꺼번에 반환하지 않고 메타+draft를 돌려준 다음 활성 문서 하나를 같은 방식으로 pull 한다. 다른 탭·세션·문서 ID 조회는 거절한다. 패널 URL에 항상 tabId가 있으므로 현재 activeSessionId 전역 폴백은 제거하고, URL 소유 탭에 열린 세션이 없으면 “세션 없음”만 반환한다.

같은 검증을 읽기뿐 아니라 PANEL_DRAFT_UPDATE·PANEL_DECISION·취소에도 적용한다. 현재는 sidepanel/*가 web_accessible_resources에 있지만 네이티브 sidePanel은 이 선언이 필요 없고 iframe 오버레이도 이미 제거됐다. 구현 시 이 WAR 항목을 삭제해 사이트가 패널 문서를 임의로 삽입할 표면도 없앤다. 패널 경로가 아니거나 URL의 tabId와 세션 소유자가 다르면 원문 조회와 상태 변경을 모두 거절한다.

실패 파일을 자동으로 빼고 보내지 않는다

파싱 실패·엔진 오류는 전송을 막는다. 사용자가 “이 파일 제거”를 누르면 그때만 나머지를 보낼 수 있다. 미지원 원본 통과도 사용자의 명시적 선택으로만 허용한다. 이 결정은 위치가 아니라 파일 id에 묶고, 패널은 files:[{id, action, unmaskedKeys}]만 SW에 보낸다. SW가 검증·산출물 생성을 마친 뒤 content에 CONTENT_BATCH_DECISION {files:[{id, action, artifactId?}]}를 중계한다. maskedBase64, 원문, Blob은 PANEL_DECISION에 싣지 않는다. 그래야 제외·재정렬·동일 파일명 상황에서도 잘못된 파일에 결정을 적용하지 않는다.

다중 경로 산출물은 결정 시점에 한 방식으로 만든다

현재 단일 경로는 엔진의 DOCX maskedFile과 SW의 MD wrapper 두 방식을 쓰지만, 다중 경로에서는 둘을 섞지 않는다. 엔진은 wrapFile=false로 텍스트와 탐지 항목만 반환하고, 완전 마스킹·부분 해제· truncated 앞부분 모두 SW가 결정 시점에 wrapMaskedFile()로 MD를 만든다. 따라서 SW 재시작 전후에도 파일명·MIME·내용이 같다. 패널은 바이너리를 만들거나 artifact ID를 고르지 않는다.

패널 미리보기와 SW 산출물은 반드시 같은 순수 함수를 쓴다. 현재 buildSegments()와 buildFinalTextFrom()가 sidepanel.js 안에만 있으므로 이를 utils/mask-segments.js로 옮긴다. 단순 이동으로는 부족하다. 현재 패널은 겹친 두 번째 항목의 꼬리를 별도 세그먼트로 만들지만 엔진의 masker.py:56~161는 validate_and_fix 뒤 겹침을 한 구간으로 합치고 confidence(동률이면 길이)가 높은 유형을 대표로 고른다. 공용 모듈에 같은 offset 보정·중복 제거·겹침 병합· 라벨 선택을 이식한 normalizeItems(text, items), 그 결과를 받는 buildSegments(text, normalizedItems, keyPrefix), buildFinalText(segments, unmaskedKeys)를 export한다. SW는 이미 module이라 (manifest의 background.type:'module', service-worker.js:18이 같은 utils/에서 import 중) 그대로 쓰면 되지만, 패널은 아직 module이 아니다 — sidepanel.html:109가 <script src="sidepanel.js"></script>라 type="module"을 붙여야 import가 성립한다. 이 전환은 실행을 defer로 바꾸고 최상위 스코프를 모듈로 가두는데, 확인해 보면 위험이 낮다: sidepanel.html에 인라인 핸들러가 없고 스크립트 태그도 이것 하나뿐이며 sidepanel.js가 window에 아무것도 붙이지 않는다. 그래도 §7 회귀에 단일 패널 동작 확인을 둔다. 그 위에서 sidepanel은 이 함수를 import해 미리보기를 만들고 SW도 같은 함수를 import해 최종 프롬프트와 문서 문자열을 만든다. 겹침·중복·역순 탐지 항목에서도 패널에 보인 최종 문자열과 artifact를 디코딩한 문자열이 바이트 단위로 같아야 한다.

엔진 응답을 저장하기 전에는 모든 항목의 유효 범위와 text 일치를 위 함수로 정규화하고, 아무것도 해제하지 않은 JS 결과가 엔진의 maskedText와 정확히 같은지 비교한다. 다르면 엔진/확장 마스킹 계약이 어긋난 것이므로 mask-contract-mismatch로 fail-closed하고 원문이나 산출물을 만들지 않는다. 일치 확인 뒤 maskedText는 중복 데이터이므로 저장 후보에서 제거한다. 이렇게 해야 “미리보기=artifact”뿐 아니라 “엔진이 판정한 완전 마스킹=확장이 재구성한 완전 마스킹”도 보장된다.

두 방식이 갈리는 지점은 코드에서 확인된다 — 엔진의 wrap_masked_file()은 DOCX 만 낸다 (masker/docwrapper.py. 같은 파일 상단 docstring 은 아직 “MD 래핑도 제공”이라 적혀 있지만 wrap_as_md 는 지워져 지금 없다 — 읽고 호출하면 실패한다). 반대로 확장의 utils/docwrapper.js 는 wrapMaskedFile() 이 곧 wrapAsMd() 라 항상 MD이고, 그 이유(파서가 이미 레이아웃을 버렸고, 마스킹 토큰이 더 명확하다)가 파일 주석에 적혀 있다. 주석이 명시하는 수신 확인 대상은 ChatGPT·Claude·Gemini·Copilot 네 곳뿐이며, Grok·Perplexity의 MD 수신은 §7에서 실측한다. 다중 경로가 MD 로 통일하는 것은 새 취향이 아니라 확장 쪽에 이미 적힌 결정을 따르는 것이다. 한 줄 선행 정리: service-worker.js:590이 wrapMaskedFile(text, mimeType, fileName, 0)으로 네 번째 인자를 넘기는데 시그니처는 인자 셋이라 0은 버려진다. 이 호출부를 masked/scanned-prefix 산출물 생성에 재사용하기 전에 지운다.

Chrome 확장 메시징은 기본적으로 JSON 직렬화이므로 Blob/File을 응답으로 보내지 않는다. 특정 Chrome 버전의 structured-clone이나 문서화되지 않은 대형 메시지 허용량에 기대지 않는다. GET_SCAN_ARTIFACT_META가 {totalBytes,mimeType,fileName,sha256}를 주고, GET_SCAN_ARTIFACT_CHUNK {artifactId,offset,maxBytes}가 원시 256KiB 이하 한 조각의 base64와 nextOffset을 돌려준다. content는 한 artifact의 Uint8Array(totalBytes)를 만들고 순서대로 채운다. 크기 근거는 원본 바이트가 아니라 텍스트다 — artifact 는 원본이 아니라 마스킹된 MD 텍스트다. 다만 MAX_TEXT_CHARS 20만 자(config.py:75)는 입력 상한이지 산출물 상한이 아니다. 마스킹은 길이를 늘린다: masker.py:53이 탐지 구간을 [{label} 마스킹]으로 치환하고, redact_map.py:9가 그 사실을 이미 적어 뒀다 — “자리표시자는 원본과 길이가 다르다(“홍길동” 3자 → “[이름 마스킹]” 8자)”. 짧은 PII가 조밀한 문서면 마스킹본이 원문보다 몇 배 길어진다. 그래서 상한은 20만 자 × 치환 확장 배수로 잡는다. 한 글자짜리 탐지가 문서를 가득 채우는 비현실적 최악에서도 수 MB가 될 수 있으므로 작은 메시지라고 가정하지 않는다. 실제 최대 placeholder의 UTF-8 길이와 MAX_TEXT_CHARS로 MAX_ARTIFACT_BYTES를 계산하고, 생성물이 그 계약을 넘으면 fail-closed한다. content는 완성한 bytes의 sha256이 meta와 같은지 확인해 File로 만든 뒤 조각 base64 참조를 버리고 다음 artifact를 요청한다. 배치 전체 base64를 한 메시지나 메모리에 동시에 두지 않는다.

artifactId는 탭·세션·문서·action에 묶인 능력 토큰이다. META/CHUNK는 응답 유실 시 재시도할 수 있도록 ACK 전까지 offset별로 멱등이며, offset 경계·최대 조각 크기·총 길이를 SW가 검증한다. content가 전체 길이와 sha256 검증 및 File 변환에 성공한 뒤 ACK_SCAN_ARTIFACT를 보내야 소비 처리한다. ACK는 descriptor의 pending→delivered 전이를 storage에 먼저 확정한 뒤 성공 응답하고, 같은 artifact의 ACK 재전송에는 같은 성공을 돌려준다. content는 ACK 성공을 받기 전에는 MAIN world 승인이나 사이트 주입을 시작하지 않는다. SW 재시작 뒤 GET은 pending만 재생성하고 delivered는 거절하므로 ACK 응답 유실·워커 재시작이 파일 중복 주입으로 이어지지 않는다. DELETE_SCAN_ARTIFACT는 실패·취소 때 받지 않은 잔여 artifact를 정리하는 용도다. 원본 통과가 명시된 파일은 content가 보존한 원래 File을 쓰며 SW 산출물로 위장하지 않는다.

결정과 세션 종료 사이에 주입 단계가 있다

PANEL_DECISION을 받으면 SW는 결정을 검증하고 artifact descriptor를 저장한 뒤 세션을 awaiting-injection으로 바꾼 상태를 먼저 영속화한다. 그 뒤 정확한 소유 문서에 CONTENT_BATCH_DECISION_READY {sessionId} 메타만 알리고, content가 GET_CONTENT_BATCH_DECISION {sessionId,clientBatchNonce}으로 promptText와 파일 descriptor를 pull한다. nonce는 runtime 메시지 안에서만 오가고 panel/MAIN world에는 보내지 않는다. READY가 유실돼도 decisionPromise의 짧은 재확인 timer가 같은 GET을 보내며, GET은 finalize 전까지 멱등이다. 패널에는 영속화 성공 뒤에만 결정 접수 성공을 응답한다. 이 시점에는 세션을 삭제하지 않는다. content가 artifact들을 받아 사이트 주입 증거를 확인한 다음 FINALIZE_MULTI_SESSION {sessionId, batchId, status, consumedIds}를 보내야 SW가 세션·artifact를 삭제한다. 성공 finalize는 batchId/nonce가 맞고 consumedIds가 세션의 delivered artifact 집합과 정확히 같을 때만 받는다. content는 성공·부분 성공·실패 모두 finalize하며, 메시지가 오지 않으면 저장된 deadline 기반 watchdog과 탭 navigation/close가 정리한다. 파일이 있는 성공 순서는 source prompt 해시 확인 → 최종 promptText 입력 → artifact META/CHUNK 조립과 ACK 전부 확인 → CONTENT_APPROVE_BATCH → 사이트 주입 및 항목별 증거 확인 → 1회용 승인으로 프롬프트 재전송 → CONTENT_CLOSE_BATCH → CONTENT_BATCH_SETTLED 확인 → finalize다. 파일이 전부 제외되어 M=0이면 MAIN 승인 단계 없이 프롬프트 재전송 증거 뒤 finalize한다. 승인 뒤 주입 전에 실패하거나 취소되면 CONTENT_ABORT_BATCH → 실패 finalize 순서로 정리한다. 일부 파일만 붙은 경우에도 프롬프트는 보내지 않고 성공/실패 ID를 finalize에 기록해 이미 붙은 파일을 자동 재주입하지 않는다. 사용자 취소는 artifact 생성 없이 즉시 종료한다.

5주입 — 여기가 제일 위험하다

검토가 끝나면 마스킹본 N개를 사이트에 넣어야 한다. 지금 injectFileWithEvidence 는 파일 1개를 넣고 "사이트가 받았다는 증거" 를 기다리는 4단계 전략(살아있는input → 합성paste → input되돌리기 → 합성drop)으로 돼 있다. 이 부분은 실사용 실패를 겪으며 여러 번 뒤집힌 코드라 건드릴 때 가장 조심해야 한다.

검토한 프롬프트와 지금 입력창이 같아야 한다

사용자는 네이티브 패널을 보는 동안 사이트 입력창을 계속 수정할 수 있다. START 때 정확한 UTF-8 원문의 sourcePromptSha256을 세션에 묶고, 결정을 적용하기 직전에 getEditorText()로 다시 읽어 같은 해시인지 확인한다. 다르면 artifact 승인·파일 주입·입력창 덮어쓰기·자동 전송을 모두 시작하지 않고 세션을 실패 finalize한 뒤 “프롬프트가 변경되어 다시 검토해야 합니다”를 표시한다. 공백 정규화로 다른 문장을 같다고 보지 말고 실제 전송에 쓰는 문자열과 같은 추출 규칙의 정확한 값으로 비교한다. 이 검사는 프롬프트 원문과 각 파일 인젝션 판정의 문맥도 함께 고정한다.

현재의 전역 boolean promptApproved도 그대로 확대하지 않는다. 파일 주입·업로드 대기 중에는 계속 blockedWhileScanning으로 제출을 막고, 실제 resubmitPrompt() 직전에만 {batchId,finalPromptSha256,expiresAt,uses:1} 1회용 승인을 만든다. submit 캡처러는 현재 에디터의 최종 promptText 해시가 맞을 때 그 승인을 동기적으로 소비해 한 이벤트만 통과시키고, 성공·예외 모두 즉시 폐기한다. 단순 true 상태를 await 구간에 걸쳐 유지하지 않는다.

부분 성공이 불명확하면 전체 재시도하지 않는다

input.files?.length === expectedCount는 필요한 수정이지만 충분하지 않다. 프레임워크가 첫 파일만 처리했을 수 있기 때문이다. watchAttachmentEvidence와 waitForAttachmentReady는 파일명별 기대 개수와 업로드 시작 증가량을 본다. 동일 파일명은 개수로 센다. 배치 주입 후 일부 성공 여부를 확정할 수 없으면 paste/drop으로 전체 배치를 다시 쏘지 않고 전송을 멈춘다. 최종 파일 N개는 모두 contentOwnedFiles에 등록하고 MAIN world에도 배치 ID와 함께 승인한 뒤 주입한다.

다중 배치의 FormData는 교체하지 않고 전 엔트리를 승인 대조한다

interceptor.js:1020의 replaceFD(fd, origName, newFile)는 val.name === origName인 File 엔트리를 전부 같은 새 파일로 바꾼다. 그리고 findFileInFD는 첫 지원 파일에서 return한다(§1 표의 그 줄이다). 그런데 §2는 동일 파일명 배치를 허용하고 §7은 “동일 이름 N개”를 테스트로 못박아 뒀다 — 같은 이름 두 개가 든 FormData에서 한 개의 마스킹본이 두 자리를 모두 덮어쓴다. MAIN/isolated world 사이에서는 같은 파일도 다른 JS 객체로 보이고 사이트가 File을 복사할 수도 있으므로 객체 동일성도 키가 될 수 없다. 각 최종 파일을 한 번씩 준비하면서 {docId,name,size,type,sha256,occurrence} 승인을 만들고, MAIN world는 fd.entries()의 모든 첨부 payload File/Blob을 순회해 바이트 해시까지 일치하는 아직 쓰지 않은 승인 하나에만 매칭한다. 사이트 adapter가 명시한 비첨부 메타 Blob만 제외할 수 있고, 모르는 File/Blob은 통과시키지 않는다. 완전히 같은 바이트의 중복 파일은 occurrence로 승인 개수만 소진한다. 모든 첨부 엔트리가 정확히 한 번 매칭되면 FormData 객체를 수정하지 않고 그대로 전송하며, 하나라도 미승인·중복 소진·추가 엔트리면 요청 전체를 막는다. 이미 content가 최종 파일을 주입했으므로 MAIN에서 다시 교체하면 오히려 multipart 필드와 사이트별 메타를 깨뜨린다. 기존 단일 파일 Layer 2 폴백의 replaceFD는 한 엔트리만 있을 때 정확한 엔트리 index/fingerprint로 바꾸도록 고치되, 미승인 파일이 둘 이상이면 독립적으로 처리하지 않고 다중 캡처 경로로 다시 첨부하라고 차단한다. 등록 JSON처럼 아직 바이트가 없는 요청은 이름+occurrence로 임시 상관관계를 만들 수 있지만, 실제 Blob/FormData 업로드에서 해시 또는 사이트별 upload ID/URL 연결을 반드시 확인하지 못하면 fail-closed한다.

MAIN world 승인은 다단계 업로드가 끝난 뒤 회수한다

현재 승인 레코드는 파일 메타 기준으로 오래 남으므로, N개를 먼저 승인한 뒤 일부만 주입되면 사용하지 않은 승인이 다음 요청에 재사용될 수 있다. CONTENT_APPROVE_BATCH {batchId, files[]}로 승인 레코드에 batchId와 위 최종 파일 fingerprint를 묶되 첫 일치 요청에서 제거하지 않는다. 사이트는 같은 파일을 등록 fetch POST /files, 실제 XHR/PUT, 재시도·청크 요청으로 여러 번 쓸 수 있기 때문이다.

수명 메시지를 세 개로 나눈다. 실제 주입 전에 취소·실패하면 CONTENT_ABORT_BATCH로 즉시 제거한다. 파일 주입 증거를 확인하고 1회용 승인으로 프롬프트 재전송을 시작한 직후 CONTENT_CLOSE_BATCH로 “새 승인 추가 금지” 상태만 표시한다. 이미 승인된 파일은 각 expected docId가 적어도 하나의 실제 업로드 체인에 결합되고 그 체인의 in-flight 수가 0이며 마지막 일치 뒤 quiet period가 지난 후 제거한다. CLOSE 직후 아직 보지 못한 파일을 quiet timer만으로 지우지 않는다. MAIN은 CONTENT_BATCH_SETTLED {batchId, uploadedIds, failedIds}를 isolated world에 돌려주고, 누락/실패가 있으면 성공으로 기록하지 않는다. hard TTL과 파일별 최대 요청 수는 최종 안전장치다. content/SW watchdog도 우선 CLOSE를 보내고, 탭 navigation/close로 document가 사라진 경우에만 즉시 폐기한다. 등록 요청→실제 업로드→정상 재시도까지는 같은 batch 안에서 허용하되, 등록 응답의 upload ID나 실제 PUT URL을 사이트별 adapter가 승인 docId에 묶는다. 이후 재시도·청크는 그 상관관계와 요청 횟수/ 바이트 범위가 맞을 때만 허용하고, batchId·fingerprint·tab/frame/document 수명 중 하나라도 다르거나 adapter가 관계를 입증하지 못하면 거절한다.

지원 파일이 있는 활성 네트워크 경로는 오류에도 fail-closed다

현재 XHR/FormData 경로의 .catch(() => _origXHRSend(...))와 fetch의 알 수 없는 결과 폴백은 처리 오류 때 원본을 보낸다(interceptor.js:950·980·1005·1156·1192). 다중 배치에서는 한 항목 오류가 FormData 전체 원본 유출로 이어질 수 있다. 보호가 켜져 있고 지원 파일이 하나라도 포함된 활성 XHR/fetch/Blob/ FormData 및 그 파일에서 파생된 arrayBuffer/FileReader/raw-binary 경로는 예외·타임아웃· 알 수 없는 action·승인/엔트리 개수 불일치 때 요청을 보내지 않는다. XHR은 원본 send를 호출하지 않고 공용 blockXHR()가 원본 abort를 호출한다. 아직 원본 send를 부르지 않은 XHR에서는 브라우저가 종료 이벤트를 내지 않을 수 있으므로 microtask에서 abort/loadend를 정확히 한 번 통지해 사이트의 Promise가 매달리지 않는지도 테스트한다. fetch는 성공처럼 보이는 가짜 200 응답이 아니라 AbortError로 reject한다. 그래야 사이트가 차단을 업로드 성공으로 오인하지 않는다. 원본 통과는 사용자가 패널에서 명시한 original action과 유효한 batch 승인으로만 가능하다. 보호 OFF와 사이트 adapter가 명시한 비대상 URL만 기존 passthrough를 유지하며, 모르는 업로드 URL은 학습 목적으로 통과시키지 않고 차단 로그와 사용자 오류를 남긴다.

남은 제품 결정 — 사이트 자체를 신뢰 경계 안에 둘 것인가

현재 isolated→MAIN 통신은 window.postMessage와 bridge token을 쓰지만 interceptor.js:48~54 주석대로 페이지 스크립트도 토큰을 읽고 승인 메시지를 흉내 낼 수 있다. batchId·해시· TTL은 실수와 오래된 승인 재사용은 줄여도 악의적인 페이지 자체를 막는 보안 경계는 아니다. 따라서 이 설계가 보장하는 범위는 신뢰한 6개 사이트의 정상 페이지 코드에서 확장 내부 오류나 원본 폴백으로 유출하지 않는 것이다. 사이트 페이지 스크립트 자체까지 공격자로 보면 MAIN world 후킹으로는 보장할 수 없고, 네이티브 프록시/브라우저 정책 같이 네트워크 경계 밖에서 강제하는 별도 아키텍처가 필요하다. 이 위협 모델 확대 여부만은 제품 범위 결정이므로 문서에서 임의로 확정하지 않는다.

완료 조건

사용자가 고른 파일 N개가 패널의 N개 항목과 ID로 대응하고, 최종 화면에 표시된 전송 M개가 사이트에도 정확히 M개, 각각 한 번만 도착해야 한다. 검사 실패·주입 증거 불명·세션 복구 실패 중 하나라도 있으면 프롬프트를 자동 전송하지 않는다. 성공·실패·취소 뒤에는 해당 세션의 메모리 산출물과 MAIN world 미사용 승인이 모두 0개이고, FINALIZE_MULTI_SESSION까지 확인돼야 한다. 성공한 업로드의 승인은 finalize 직후가 아니라 모든 expected docId의 업로드 체인이 settled되고 in-flight 0 + quiet period가 지난 뒤 0개가 되어야 하며 hard TTL을 넘겨 남아서는 안 된다. hard TTL이나 요청 한도 때문에 먼저 닫힌 batch는 성공 완료로 세지 않는다. truncated 파일은 사용자가 선택한 범위와 실제 전송 내용이 정확히 일치해야 한다. 이 조건을 6개 사이트에서 만족해야 다중 첨부 완료로 본다.
