회사 기밀 온톨로지 — 설계 계획

Campfire 게이트웨이 · 2026-09-07 · 확정: 문서 자동추출 + 사람 승인 / 데모로 시작해 실사용까지

v2 로 대체됨

전제가 바뀌었다 — 온톨로지는 고정, 회사 데이터로 KG 를 채운다. v2 계획서를 보라. 이 문서의 §2 선행연구와 §5 한국어 경계는 그대로 유효하고 v2 가 참조한다.

지금 게이트웨이는 개인정보·자격증명·인젝션을 막는다. 회사 기밀은 그대로 통과한다. 제품 로드맵도, 고객사 단가표도, 미공개 코드명도 외부 AI 서비스로 나간다. 이 문서는 그것을 온톨로지로 잡기 위한 설계안이다.

새로 만들 것이 생각보다 적다. 코드를 읽어보니 배관은 사실상 다 깔려 있다.

결론

새로 만들 것은 ① 온톨로지 데이터 ② 매처 ③ 편집 수단 셋뿐이다. 파이프라인·마스킹·UI·저장소는 손대지 않는다.

1왜 사전이 아니라 온톨로지인가

이 프로젝트에서 이미 두 가지 탐지 방식을 써봤고, 회사 기밀은 둘 다 안 맞는다.

대상방식근거
자격증명 #147 해결정규식형태가 규격이다 — AKIA…, ghp_…
주소 #143 미탐NER 모델형태가 없어 판단이 필요한데, 그 판단이 틀렸다
회사 기밀?보편 형태도 없고 보편 모델도 없다

세 번째 줄이 핵심이다. “오로라”가 기밀인지 아닌지는 회사마다 다르다. 어떤 모델도 이걸 학습할 수 없다 — 정답이 회사 안에만 있기 때문이다.

그런데 단순 용어 목록(flat list)으로도 안 된다. 진짜 위험한 것은 조합이다.

"오로라" → 자연현상. 안전 "매출" → 흔한 단어. 안전 "삼성전자" → 공개 정보. 안전 "오로라 프로젝트 삼성전자 납품 단가 12,400원" ← 기밀

어느 단어도 단독으로는 기밀이 아닌데 합치면 기밀이다. 필요한 것은 어떤 종류의 것들이 어떤 관계로 같이 나올 때 위험한가이고, 그게 온톨로지다. 사전은 이걸 표현할 수 없다.

2선행 연구가 말하는 것

설계를 논문에 대봤다. 다섯 군데가 바뀌었고, 한 군데는 근거가 생겨 더 강해졌다.

발견설계에 미친 영향
quasi-identifier — 우편번호·생년월일·성별 세 개로 미국인 86% 이상이 식별된다 solo 축에 이름이 있었다. 조합 규칙은 부가기능이 아니라 1급 기능
키워드·규칙 방식은 실제 민감정보의 “작은 일부만” 잡는다 LLM 확장을 선택 → 필수 로 승격
최신 트랜스포머 용어추출도 F1 41.9~59.1 자동 채움은 불가능. 추출과 탐지의 목표를 반대로 잡는다
중첩 용어 라벨링이 재현율을 크게 올린다 최장일치 + 중첩 후보 승격. 랭킹에 C-value 도입
LLM 은 클래스·개체는 찾지만 관계는 빠뜨리거나 지어낸다 LLM 에게 관계를 만들게 하지 않는다 — 타입 분류만 시킨다
선행 온톨로지-DLP 는 대부분 “공격·이벤트” 온톨로지 우리는 콘텐츠 온톨로지 — 빈 칸이 거기 있다

① 조합 위험에는 정본이 있다 — quasi-identifier

Sweeney 의 고전적 결과: 각각은 식별자가 아닌 속성 세 개의 조합만으로 미국 인구의 대부분이 특정된다. 프라이버시 문헌은 이걸 quasi-identifier 라 부르고, “단독으론 민감하지 않지만 결합하면 민감해지는 것”을 1급 개념으로 다룬다.

내가 solo: none / low 로 부른 축이 바로 이것의 기밀 버전이다. 즉흥적으로 만든 장치가 아니라 확립된 개념이었다는 뜻이고, 따라서 조합 규칙은 “여유되면 붙이는 것”이 아니라 설계의 뼈대다. 같은 문헌이 “키워드 기반은 문맥 없는 민감정보만 잡는다”고 못 박는다 — 사전만으로는 원리적으로 부족하다.

② 사전 방식의 재현율 천장은 측정된 사실이다

Neerbek(2020)은 민감정보 탐지에서 “부서지기 쉬운 규칙 집합은 실제 민감정보의 작은 일부만 찾아낸다”고 직접 말한다. 문맥 인코딩 신경망이 키워드 계열을 유의미하게 앞선다는 것이 그 논문의 결론이다.

설계 변경 — LLM 확장은 선택이 아니다

1~2단계(사전+관계)만 내놓고 “기밀을 막는다”고 하면 그건 과장이 된다. #143 주소 미탐과 같은 실패 유형 — 지원한다고 선언했는데 조용히 새는 것. LLM 확장을 필수, 다만 순서상 마지막으로 옮긴다. 로컬 전용 제약은 그대로다.

다만 Neerbek 의 전제 하나는 우리에게 안 맞는다. 그는 “생성 규칙이나 주제 시드 단어에 접근 가능하다는 비현실적 가정”을 비판하는데, 기업 배치에서는 그 시드를 줄 사람이 실제로 있다 — 보안담당자다. 우리 재현율 천장은 그의 설정보다는 높다. 그래도 천장은 천장이다.

③ 추출과 탐지는 목표가 반대다

용어 자동추출(ATE)의 현재 수준을 보고 기대치를 고쳤다. ACTER 벤치마크에서 최신 트랜스포머 계열이 F1 약 41.9~59.1이다. 최고 시스템도 절반 남짓 맞힌다.

그래서 설계 원칙 하나를 명시한다

추출 단계 재현율 우선 → 사람이 기각하기는 쉽다 탐지 단계 정밀도 우선 → 오탐은 사용자 신뢰를 깎는다

두 단계의 목표가 반대다. 그리고 F1 60 짜리 파이프라인의 출력을 사람 승인 없이 온톨로지에 넣는 설계는 애초에 성립하지 않는다 — 승인 UI 는 편의기능이 아니라 정확도 요구사항이다.

④ 중첩 용어를 처음부터 다룬다

ATE 에서 C-value/NC-value 라는 지표가 만들어진 이유 자체가 중첩 다중어 용어다. 최근 연구도 중첩 용어 라벨링을 넣자 재현율이 크게 올랐다고 보고한다. 우리 사례로 옮기면:

오로라 ⊂ 오로라 프로젝트 ⊂ 오로라 프로젝트 2차 단가표 ↑ ↑ ↑ 흔한 단어 진짜 코드명 가장 위험한 형태

두 가지가 바뀐다. 매처는 최장일치(maximal munch)로 가장 긴 것을 잡고, 중첩된 짧은 후보는 별도 인스턴스로 승격할 수 있게 남긴다. 후보 랭킹은 내가 처음에 쓴 “문서 간 분포”보다 검증된 C-value 를 쓴다 — 긴 용어 안에 자주 파묻히는 조각을 자동으로 깎아준다.

⑤ LLM 에게 관계를 만들게 하지 않는다

LLM 기반 온톨로지 학습(LLMs4OL 계열)의 보고된 실패 모드가 정확히 우리가 피해야 할 것이다.

  • 클래스와 개체는 잘 찾지만 클래스 간 속성을 빠뜨리고, 개체 간 관계를 틀리게 만든다
  • 문장 단위 프롬프트는 정확도가 오르는 대신 환각도 늘어난다
  • 초기 단계 오류가 뒤 단계로 전파된다 — 용어추출·타입지정이 이후 전부를 오염시킨다

원래 계획에서 관계를 동시출현 통계로 뽑기로 한 것은 “싸서”였는데, 이제 그게 문헌이 지목한 LLM 약점을 정면으로 회피하는 선택이 됐다. 셋 다 대응된다.

보고된 실패우리 대응
관계를 틀리게 만든다LLM 은 타입 분류만. 관계는 동시출현 통계로만 제안
문장 단위 → 환각 증가문장 단위는 유지(정확도 이득), 환각은 사람 승인이 막는다
초기 오류가 전파된다candidates.yaml / company.yaml 파일 분리가 전파 경로를 끊는다

⑥ termhood 의 정석은 배경 코퍼스다 — 없이 가되, 구멍은 뚫어둔다

termhood 지표(TF-IDF, C/NC-value, 엔트로피, 상호정보량)는 상당수가 참조 코퍼스를 전제한다. 우리는 없이 시작한다(토크나이저 파편화 + 문서 간 분포 + C-value). 대신 스키마에 배경 코퍼스 경로 한 줄을 미리 뚫어둔다 — 비용 0, 실측에서 부족하면 그때 채운다.

⑦ 포지셔닝 — 빈 칸이 어디 있나

  • 온톨로지 기반 DLP 선행 연구는 대체로 공격·이벤트 온톨로지다 — 저수준 이벤트를 MITRE ATT&CK 전술과 상관시키는 식. 데이터 내용의 의미를 모델링하지 않는다
  • 로컬 LLM 익명화 연구는 실제로 잘 된다(로컬 Phi/LLaMA 로 민감내용 91%+ 탐지 보고). 그런데 대상이 GDPR·HIPAA 규제 개인정보다 — 회사 고유 기밀은 다루지 않는다
  • 지문(fingerprinting) 방식은 재작성·경미한 수정으로 우회되고, 문서 전체를 지문화해 오탐이 난다고 보고된다

즉 회사마다 다른 콘텐츠 기밀을, 로컬에서, 사용자 검토를 끼워서 막는 조합은 선행 연구들 사이의 빈 칸이다. 이게 이 기능의 자리다.

이 설계에서 제일 중요한 한 가지

solo 축이다. 온톨로지 기반 탐지가 실패하는 이유는 언제나 오탐 폭발이고, “오로라”를 등록하는 순간 오로라 사진 얘기까지 전부 마스킹된다. solo: none/low 인 항목은 관계나 트리거가 붙을 때만 발화한다. 클래스 기본값을 인스턴스가 덮어쓸 수 있게 해서, 흔한 단어 하나 때문에 클래스 전체를 포기하지 않아도 되게 한다.

이건 프라이버시 문헌의 quasi-identifier 를 기밀 쪽으로 옮긴 것이다(§2-①). 즉흥적 장치가 아니라 확립된 개념이라, solo 를 스키마의 1급 필드로 둔다 — 클래스·인스턴스 양쪽에서 지정 가능하고, 값이 없으면 mid 가 아니라 low 로 떨어진다. 등록만 하고 위험도를 안 정한 항목이 조용히 전면 마스킹되는 쪽으로 기울면 안 된다.

  • 청크를 타지 않는다 — 관계 규칙이 문장·문단을 넘나든다. 자격증명이 PEM 블록 때문에 원문 전체를 보는 것과 같은 이유
  • 타입 상수 CONFIDENTIAL 을 PII_TYPES 에 추가 → 마스킹·패널·저장소·API 계약이 전부 무변경으로 붙는다. CREDENTIAL 이 이미 만든 선례
  • 라벨은 클래스명까지 노출: [회사기밀:프로젝트 코드명 마스킹] — 사용자가 해제 여부를 판단하려면 무엇이 가려졌는지 보여야 한다

ponytail 천장

기밀에 별도 정책(block vs mask)이 필요해지면 그때 confidentialItems 로 분리한다. 지금 분리하면 익스텐션·패널·store·테스트까지 diff 가 번지는데 사용자가 얻는 게 없다.

5한국어에서 실제로 어려운 지점

여기를 대충 넘어가면 1단계가 통째로 못 쓰게 된다.

  1. 조사 — “오로라의”, “오로라를”는 잡아야 하고 “오로라기”(다른 단어)는 버려야 한다. Aho-Corasick 매치 뒤 1글자가 한글인데 조사 목록에 없으면 폐기.
  2. 표기 흔들림 — “오로라프로젝트” / “오로라 프로젝트” / “Aurora”. 정규화 키(공백·하이픈 제거 + 소문자)로 별칭을 자동 확장해서 등록자가 일일이 안 적게 한다.
  3. 영문 약어 오탐 — “SEC”가 고객사 별칭이면서 미국 증권거래위원회다. 영문 2~3글자 별칭은 solo 를 강제로 한 단계 낮춘다.
  4. 중첩 용어 연구 반영 — 짧은 용어가 긴 용어 안에 묻힌다. 매처는 최장일치(maximal munch) 로 가장 긴 것을 잡되, 안에 묻힌 짧은 후보를 버리지 않고 별도 인스턴스로 승격할 수 있게 남긴다.
오로라 ⊂ 오로라 프로젝트 ⊂ 오로라 프로젝트 2차 단가표 ↑ ↑ ↑ 흔한 단어 진짜 코드명 가장 위험한 형태

이게 §2-④ 에서 온 변경이다. ATE 에서 C-value 라는 지표가 만들어진 이유 자체가 중첩 다중어 용어였고, 최근 연구도 중첩 용어 라벨링을 넣자 재현율이 크게 올랐다고 보고한다. 등록자가 “오로라 프로젝트”를 넣었는데 “오로라 프로젝트 2차 단가표”를 놓치면 가장 위험한 형태를 정확히 놓치는 셈이다.

ponytail 천장 — 형태소 분석기

한국어 NER 의 정석은 형태소 단위 처리이고, 어절에서 조사 같은 기능형태소를 개체명에서 제외하는 것이 표준 어노테이션이다. 우리는 분석기(kiwi·mecab) 의존성을 추가하지 않고 “매치 우측 경계 = 조사 목록” 휴리스틱으로 간다. 실측에서 경계 오류가 나오면 그때 kiwi 를 넣는다 — 지금 넣으면 설치 용량과 빌드 복잡도를 미리 지불하는 것이다.

6단계

단계내용크기
0 스키마 확정클래스 8종 + YAML 스펙 + 샘플 파일. 코드 0줄지금 이 문서
1 사전 매칭로드 · AC 매처 · solo 판정 · 조사 처리 + 테스트~180줄
2 관계 규칙같은 문단 내 관계 결합 → 위험도 상승. 같은 파일~60줄
3 후보 추출 핵심문서 폴더 → C-value 랭킹 → 클래스별 후보 + 관계 후보. §8~220줄
4 승인 + 그래프 뷰후보 승인/기각 UI, 온톨로지 그래프. §9~200줄
5 LLM 확장 필수미등록 표현까지 — 로컬 EXAONE 만. §2-② 재현율 천장별도 판단

1~2단계는 실사용 품질로 만들고, 4단계 그래프 뷰가 데모 임팩트를 챙긴다. 버려지는 코드가 없다 — 그래프 뷰는 실사용에서도 “우리 회사 기밀이 이렇게 얽혀 있다”를 보여주는 관리 화면이 된다.

5단계(LLM 확장)에 미리 못 박아야 하는 제약

인젝션 탐지는 2차 위치특정을 외부 Solar API 로 보낸다(PII 는 가리고 보낸다). 기밀 탐지는 외부 API 를 쓸 수 없다 — 기밀이 새는 걸 막는 기능이 기밀을 외부로 보내면 앞뒤가 안 맞는다. 로컬 모델만.

7검증

engine/tests/test_ontology.py — 가상 회사 온톨로지 하나로 세 가지를 본다.

  • 재현율 — 등록 용어 · 별칭 · 조사 결합 · 관계 결합이 잡히는가
  • 정밀도 — solo: none 단어가 단독으로 나왔을 때 안 잡혀야 한다. 이게 제일 중요하다
  • 계약 — 온톨로지 파일이 없으면 조용히 0건. 기능이 꺼진 상태로 정상 동작해야 한다

8후보 추출 — “빈 온톨로지 문제”

온톨로지 기반 제품이 실패하는 두 번째 이유는 오탐이 아니라 아무도 안 채운다는 것이다. 보안담당자에게 빈 폼을 주면 용어 300개를 손으로 적지 않는다. 그래서 회사 문서에서 뽑아 승인만 받는다.

입력은 사용자가 지정한 폴더 하나. 파서는 이미 8종(docx·pdf·xlsx·pptx·hwp·hwpx·txt·stubs)이 있으니 그대로 쓴다.

신호 네 개를 겹친다

#신호비용
1기밀 표식 문서 우선 — “대외비 / 사외비 / 내부한정 / Confidential / Internal Only”공짜
2PII 모델 재사용 — 이미 뱉는 ORGANIZATION 라벨 → CLIENT 후보공짜
3고유성 랭킹 — C-value + 토크나이저 파편화 연구 반영공짜
4로컬 LLM 타입 분류 — 1~3 으로 좁힌 후보에만배치

이 단계의 목표는 탐지와 반대다

추출(여기) 재현율 우선 → 사람이 기각하기는 쉽다 탐지(1~2단계) 정밀도 우선 → 오탐은 사용자 신뢰를 깎는다

§2-③ 에서 온 원칙이다. 최신 트랜스포머 용어추출도 F1 이 60 언저리라 여기서 정밀도를 노리는 건 헛수고다. 넓게 건지고 사람이 쳐내게 한다.

1번이 가장 저평가된 신호다. 회사는 이미 자기 기밀 문서에 도장을 찍어 놨다. 그 표식이 있는 문서만 먼저 훑으면 후보 노이즈가 통째로 줄어든다.

3번 — 배경 코퍼스 없이 고유성을 재는 법. 처음엔 “문서 간 분포”를 쓰려 했는데, 같은 문제를 이미 푼 검증된 지표가 있어 바꿨다.

  • C-value — 빈도에 중첩 보정을 더한 termhood 지표. 긴 용어 안에만 자주 파묻히는 조각(“오로라” 자체)의 점수를 자동으로 깎고, 독립적으로도 등장하는 것을 올린다. 문서 간 분포보다 정확히 우리 문제(§5 중첩 용어)에 맞는다
  • 토크나이저 파편화 — PII 인코더 백본의 서브워드 사전은 일반 한국어로 학습돼 있다. 흔한 단어는 1~2 토큰으로 끝나고, 회사가 지어낸 코드명은 여러 조각으로 부서진다. tokenizer.json 은 이미 필수 파일이라 새 데이터 0으로 얻는 고유성 지표다

ponytail 천장

제대로 된 TF-IDF 를 하려면 일반 한국어 배경 코퍼스가 필요하다. 위 두 신호가 실측에서 부족할 때 추가한다. (모델의 gazetteer.json 은 배경 코퍼스가 아니다 — 학습셋의 PII 표면형 사전이라 용도가 다르다. 다만 이미 PII 로 잡히는 것을 후보에서 빼는 데는 쓸 수 있다.)

4번 — LLM 을 여기서만 쓰는 이유. 전체 문서를 LLM 에 넣지 않는다. 1~3 으로 좁힌 후보와 그 주변 한 줄만 넣고 “이 후보는 클래스 8종 중 무엇인가, 아니면 아무것도 아닌가”를 묻는다. 그리고 결정적으로 이건 오프라인 배치라 실시간 경로의 속도 제약이 없다 — 게이트웨이는 초 단위로 답해야 하지만 온톨로지 구축은 몇 분 걸려도 된다.

관계는 동시출현으로 자동 제안

승인된 인스턴스 A, B 가 같은 문단에 N회 이상 함께 등장 ↓ 관계 후보 [A, ?, B] → 사람은 이름만 붙인다 ("납품처") 안 붙여도 무명 관계로 작동한다

온톨로지가 손으로 그리는 그림이 아니라 데이터에서 자라는 그래프가 되는 지점이다. 동시출현 세기라 계산도 싸다.

싸서 고른 게 아니라, 이제는 근거가 있다

원래는 “동시출현이 싸니까”였다. §2-⑤ 를 보고 나니 이게 LLM 온톨로지 학습의 보고된 최대 약점을 정면으로 회피하는 선택이었다 — LLM 은 클래스와 개체는 잘 찾지만 관계를 빠뜨리거나 지어낸다. 그래서 LLM 에게는 타입 분류만 시키고 관계는 통계로만 뽑는다. 각 역할을 잘하는 쪽에 준다.

출력과 안전장치

company.candidates.yaml — 승인 대기열을 파일부터 분리한다. 탐지기는 company.yaml 만 읽는다. 승인되지 않은 후보가 실수로 탐지에 쓰이는 경로가 아예 없어야 한다.

추출 대상 문서는 기기를 떠나지 않는다 — 파싱·NER·LLM 전부 로컬, 외부 API 0회. §6 의 제약과 같은 이유다.

9승인 화면과 그래프 뷰

승인 화면 — 근거가 핵심

후보 1건에 용어 · 제안 클래스 · 근거 문장 1개 · 출현 문서 수를 함께 보여준다. 근거 없이 “‘오로라’를 승인하시겠습니까”만 물으면 판단이 불가능하다. 버튼은 승인 / 기각 / 클래스 변경 셋.

그래프 뷰 — 데모 임팩트

networkx 가 이미 설치돼 있다(torch 경유). 서버에서 레이아웃 좌표만 계산해 내려주고 렌더러는 SVG 로 그린다 — Electron CSP 안에서 외부 라이브러리를 로드할 필요가 없다.

  • 노드 = 인스턴스(클래스별 색), 엣지 = 관계
  • 탐지가 발화하면 그 노드와 엣지가 빛난다 → “왜 막혔는지”가 한 장으로 보인다

이건 데모용 장식이 아니다. 실사용에서도 “우리 회사 기밀이 이렇게 얽혀 있다”를 보여주는 관리 화면으로 그대로 남는다.

10다음

0단계는 이 문서로 끝난다. 넘어가기 전에 확인할 것 두 가지:

  1. 클래스 8종이 맞나 — 이 회사(혹은 데모 시나리오)에 없는 범주가 있거나, 빠진 게 있는가
  2. solo 기본값이 맞나 — 특히 CLIENT(low)와 FINANCIAL_METRIC(none). 여기가 오탐률을 결정한다

확정되면 1단계부터 시작한다. 1~2단계는 모델 기동 없이 테스트된다 — 사전 매칭과 관계 규칙은 순수 파이썬이라 GPU 도 가중치도 필요 없다.

연구를 보고 나서 정직하게 남는 것

1~2단계만으로는 “회사 기밀을 막는다”고 말하면 안 된다. 사전·규칙 방식의 재현율 천장은 측정된 사실이고(§2-②), 우리 조건이 그 논문보다 유리하긴 해도 천장은 천장이다. 1~2단계는 “등록된 기밀은 확실히 막는다”이고, 그 이상은 5단계 이후다 — #143 이 가르쳐준 것은 선언과 실제가 벌어지면 그게 조용한 실패라는 것이었다.
