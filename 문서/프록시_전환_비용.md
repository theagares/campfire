# 프록시 가로채기로 전환할 때의 비용

2026-09-20 · Chrome 확장 → 로컬 TLS 프록시(MITM)

## 한 줄

**측정해 보니 비싼 항목이 거의 없다.** 운영 비용도, 최대 위험이던 ChatGPT 업로드도 실측으로 값이 내려갔다.

---

## 1. 새로 드는 비용 — 얼마나 드나

| 항목 | 얼마 | 근거 |
|---|---|---|
| **루트 CA 설치** | **관리자 불필요.** 사용자 저장소면 된다. 기기당 1분, 경고창 1회 | 측정 — `CurrentUser\Root` ReadWrite 열림(59개), `LocalMachine\Root`는 Access denied |
| **프록시 지정** | **관리자 불필요.** HKCU 키, 기기당 수 초 | 측정 |
| **QUIC 차단** | **비용 0.** 프록시를 지정하면 Chrome이 알아서 TCP로 간다 | 측정 — 죽은 프록시에 gemini·claude·chatgpt **셋 다 `ERR_PROXY_CONNECTION_FAILED`**. h3 사이트도 우회 안 함 |
| **백신 충돌** | 이 PC는 Defender 단독, 사용자 저장소 CA 설치를 막지 않음 | 측정 — 타사 EDR 없음. 기업 EDR은 미확인 |
| **HITL 보류** | 스캔은 **0.2초**라 무시 가능. 나머지는 전부 사람 판단 시간 | 측정 — warm 161~186ms |
| **검토 UX 이동** | 패널이 앱 창으로. `sidepanel.js` 984줄 재사용 | 2~3 인·주 (추정) |
| **실패 모드 역전** | 프록시가 죽으면 **그 사이트 전체 불가** (지금은 요청 단위 fail-closed) | 측정 — 위 `ERR_PROXY_CONNECTION_FAILED`가 그 모습 |
| **배포 형태** | 기기별 로컬이면 위 그대로. **회사 게이트웨이면 HITL이 사실상 불가** | — |

**기기당 설치는 관리자 권한 없이 2분 안쪽.**

---

## 2. 없어지는 것 — 4,000줄 이상

주입(injection) 문제가 통째로 사라진다. 지금 코드의 가장 아픈 부분은 전부 "우리가 마스킹본을 **다시 넣어야** 한다"에서 나오는데, 프록시는 날아가는 요청을 고치므로 그 문제가 없다.

- `content.js` 2,695줄 중 **약 1,370줄(51%)** 이 주입 기계 (증거 체인 819 + `setEditorText` 273 + `waitForAttachmentReady` 114 + `reviveFileInput` 84 + 진단 82)
- `interceptor.js` 2,344줄 거의 전부 (`requestProcessing` 547 + `_fetchLooksLikeUpload` 264 + `_interceptPromptSubmit` 249 + 후킹부)
- SW의 lease 큐·artifact 토큰·배치 승인 수명
- `bridgeToken`, `contentOwnedFiles` 자기 삼킴 방지, `promptApproved` 게이트

**남는 것:** 엔진, 모델, `mask-segments`, `docwrapper`, 마스킹 계약.

## 3. 사이트별 비용

| 사이트 | 형태 | 난이도 |
|---|---|---|
| Claude / Copilot / Perplexity / Gemini(파일) | FormData | 낮음 (mitmproxy가 multipart 파싱 제공) |
| Grok | JSON + base64 | 낮음 |
| Gemini (프롬프트) | `batchexecute` 중첩 JSON 배열 | 중간 |
| ChatGPT | 등록 → Azure PUT → 확인 | **낮음 (실측으로 내려감)** |

### ChatGPT — 실측으로 해결됨

앞 판에서 "에뮬레이션이 필요할 수 있다"고 쓴 항목이다. 실제로 재봤다 (`probe/chatgpt-upload-protocol` 브랜치).

| 선언 크기 | 실제 PUT | Azure PUT | 처리 결과 |
|---|---|---|---|
| 4096 (과대) | 17B | 201 | ❌ error |
| 216 (일치) | 216B | 201 | ✅ completed |
| 20 (과소) | 216B | 201 | ❌ **`file_size_mismatch`** |
| 1024 (재작성) | 1024B (내용 107B + 공백 917B) | 201 | ✅ completed |

- **Azure는 크기를 안 본다** — 불일치해도 PUT은 201. 검증은 ChatGPT 백엔드가 한다
- **검증은 정확 일치** — 과대·과소 **둘 다** 거부. "넉넉히 선언하고 통과하길 기대"하는 방법은 **죽었다**
- **패딩이 통한다** — 선언값과 본문 크기만 맞으면 인덱싱까지 끝난다

**그래서 프록시가 할 일은 두 줄이다:** 등록의 `file_size: N` 을 `N'` 으로 재작성하고, 마스킹 결과를 정확히 `N'` 바이트까지 패딩해서 PUT한다. 가짜 SAS URL도, 프록시가 대신 업로드하는 것도 필요 없다.

## 5. 아직 못 잰 것

- **`N'` 산정.** 마스킹은 텍스트를 늘린다(`redact_map.py:9`: 3자 → 8자). `N'` 이 마스킹 결과보다 작으면 실패하므로 배수와 초과 시 폴백이 필요하다
- **DOCX 패딩.** 공백 패딩은 텍스트에서 안전하고 확장의 `wrapMaskedFile()` 은 항상 MD를 내지만, ZIP 계열은 검증 안 했다
- **큰 파일 멀티파트.** 클라이언트가 `supports_direct_azure_multipart: true` 를 선언한다. 작은 파일로만 쟀다
- **사이트 JS의 abort 타임아웃.** 사람이 얼마나 오래 볼 수 있는지의 상한. 실제 요청을 붙들어 봐야 안다
- **데스크탑 앱.** 이 PC에 없어 못 쟀다. 각 앱이 시스템 프록시를 따르는지는 별개 문제

## 6. 권고

엔진이 FastAPI이므로 mitmproxy 애드온에서 `run_pipeline`(`orchestrator.py:185`)을 in-process 호출한다. `adapters/proxy/`를 `http_api`·`mcp` 옆에 더하고 엔진·모델은 손대지 않는다.

**최대 위험이던 ChatGPT가 내려갔으니 남은 판단은 제품 쪽이다** — 검토 UI가 페이지 옆에서 앱 창으로 가는 것을 감수할지, 그리고 프록시가 죽으면 사이트 전체가 막히는 실패 모드를 받아들일지.
